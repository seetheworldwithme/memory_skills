# Memory 与 Skill 治理产品架构及迭代路线图

> 状态：已确认
>
> 日期：2026-08-20
>
> 范围：TencentDB Agent Memory，重点覆盖 `MemoryCore` 的 Chat Memory 与 Skill
>
> 路线选择：治理可信优先

## 1. 文档目的

本文基于当前 Chat Memory 与 Skill 的设计优缺点，给出后续产品和架构迭代方向。

本文不展开到具体源码文件、接口字段和编码任务，而是回答以下问题：

- 产品下一阶段最重要的问题是什么；
- Memory 与 Skill 应该形成怎样的统一架构；
- 哪些能力应优先建设，哪些能力应暂缓；
- 如何衡量改造是否真正改善了用户体验；
- 如何在个人、团队和高风险场景之间取得平衡。

相关分析：

- [Chat Memory 设计理念、优点与缺点](../analysis/chat-memory-design-pros-cons.md)
- [Skill 设计理念、优点与缺点](../analysis/skill-design-pros-cons.md)

## 2. 核心判断

当前系统的主要优势是捕获能力和工程完整性：

- L0-L3 分层记忆同时保留原始证据、原子事实、场景总结和长期画像；
- Skill 能够把历史对话中的经验沉淀为版本化、可检索、可携带资源的执行资产；
- 捕获、抽取、召回、队列、存储和降级能力已经形成较完整的工程体系。

当前最需要解决的问题不是“怎样记住更多”，而是：

> 怎样确保真正影响 Agent 的长期信息是可解释、可修正、可撤销、可删除并且与当前任务相符的。

如果继续优先扩大捕获率和自动化程度，系统会积累更多重复、冲突、过期和低置信资产。错误 L1 还可能被进一步归纳为 L2/L3，低质量对话也可能直接生成正式 Skill，最终形成错误固化。

因此，后续路线应从“捕获优先”逐步转向“可信治理优先”：

1. 先建立来源、置信度、状态和删除传播能力；
2. 再建立候选审批、冲突和过期治理；
3. 然后优化统一召回和 Skill 路由；
4. 最后利用真实任务反馈实现受控的自我改进。

## 3. 产品目标

### 3.1 总目标

构建一个可信的长期 Agent 资产系统，使 Memory 与 Skill 满足以下要求：

- 用户知道系统记住了什么；
- 用户知道信息为什么被记住、来源在哪里；
- 用户能确认、纠正、删除和撤销长期资产；
- Agent 能区分原始事实、模型推断和行为规则；
- 错误不会静默升级为长期画像或正式 Skill；
- 高风险任务只受经过确认的行为规则影响；
- 系统能根据实际使用效果淘汰低价值资产。

### 3.2 非目标

本路线当前不以以下事项为主要目标：

- 最大化记忆写入数量；
- 最大化 Skill 自动创建数量；
- 增加更多记忆层级；
- 用更大模型替代数据治理；
- 让 Agent 无监督地直接重写所有正式资产；
- 一次性重构所有存储和运行模式。

## 4. 统一产品架构

建议把 Memory 与 Skill 统一纳入四层产品架构。

```text
┌──────────────────────────────────────────────┐
│ Delivery Layer                              │
│ 召回、Skill 路由、上下文预算、风险策略、解释 │
├──────────────────────────────────────────────┤
│ Governance Layer                            │
│ 晋升、审批、冲突、过期、删除传播、敏感检测   │
├──────────────────────────────────────────────┤
│ Knowledge Layer                             │
│ L1/L2/L3、Draft/Verified Skill、版本与关系   │
├──────────────────────────────────────────────┤
│ Evidence Layer                              │
│ L0 原始对话、消息引用、生成日志、操作审计    │
└──────────────────────────────────────────────┘
```

### 4.1 Evidence Layer：证据层

证据层保存原始事件和可复现引用，包括：

- L0 原始对话；
- 来源消息 ID；
- 会话、任务、Agent 与用户身份；
- 抽取和生成时间；
- 使用的 Prompt ID、版本和内容哈希；
- Memory 与 Skill 的写入、修改和删除审计。

证据层的职责是回答“这条长期信息从哪里来”，不应直接把原始内容当作长期行为规则。

### 4.2 Knowledge Layer：知识资产层

知识资产层保存所有可能影响未来 Agent 的内容：

- L1 原子记忆；
- L2 场景记忆；
- L3 Persona；
- Draft Skill；
- Verified Skill；
- Skill 的版本和辅助资源。

每个长期资产都应具有统一治理元数据：

- 资产类型；
- 作用域；
- 生命周期状态；
- 来源引用；
- 置信度；
- 创建原因；
- 最近验证时间；
- 有效时间范围；
- 派生关系；
- 冲突关系；
- 敏感等级；
- 最近使用时间与使用效果。

### 4.3 Governance Layer：治理层

治理层是后续最关键的新能力，统一负责：

- Draft 到 Verified 的晋升；
- 用户或管理员审批；
- 记忆与 Skill 冲突检测；
- 过期和降权；
- 相似资产合并建议；
- L0 删除后的派生资产处理；
- Secret、PII 和敏感信息扫描；
- 团队与高风险作用域的发布控制；
- 错误资产回滚与影响分析。

### 4.4 Delivery Layer：交付层

交付层负责决定本轮 Agent 实际看到什么：

- 召回哪些 L1；
- 是否注入 Persona；
- 是否展示 Scene Navigation；
- 路由哪些 Skill；
- 每类资产占用多少上下文预算；
- 低置信内容以提示还是指令形式出现；
- 当前任务是否只允许使用 Verified Skill；
- 如何向 Agent 和用户解释召回原因。

交付层必须保留类型边界，不应把事实、推断和行为规则渲染成同一种权威内容。

## 5. 统一生命周期

### 5.1 建议状态

Memory 与 Skill 共享以下基础状态：

```text
Draft
  ├─→ Verified
  │     ├─→ Deprecated
  │     └─→ Archived
  ├─→ Rejected
  └─→ Archived
```

状态定义：

| 状态 | 含义 | 是否可影响 Agent |
| --- | --- | --- |
| Draft | 自动抽取或待确认候选 | 仅低风险提示，不作为强规则 |
| Verified | 已确认或满足严格自动晋升条件 | 可以正常参与召回与路由 |
| Deprecated | 仍有历史价值，但已不推荐使用 | 默认不主动注入 |
| Rejected | 用户或治理规则明确拒绝 | 不参与召回，保留审计 |
| Archived | 已归档或超出保留期 | 不参与召回，可按策略物理清理 |

### 5.2 不同资产的晋升条件

#### L1 原子记忆

可自动进入 Draft。满足以下条件之一后可以晋升：

- 用户明确确认；
- 在多个独立会话重复出现；
- 来自确定性工具结果且来源可信；
- 与已有高置信事实一致并通过冲突检查。

> 落地状态（2026-08-21）：已实现规则化自动 Verify——`src/governance/auto-verify.ts`
> 以用户预配的确定性规则组合（证据角色白名单 / 层级 / 置信度 / 与证据原文的
> bigram 重合度 / 可选多会话佐证，取"全部满足"而非"之一"，比本节条件更保守）
> 放行 L1 Draft，资产标记 `verifiedBy=auto`，incorrect/outdated 反馈自动降级
> 待复核；多会话佐证规则按 `evidence.origin_session_id` 去重计数。配置与语义
> 见 README「规则化自动 Verify」。Skill 自动晋升未落地（v1 永远人工审核）。

#### L2 场景记忆

由多个 L1 派生，不能只因一次抽取成功就视为强事实。应保留引用的 L1 集合和覆盖时间范围。

#### L3 Persona

采用最严格的晋升条件：

- 跨多个会话和时间段重复出现；
- 不与近期用户明确陈述冲突；
- 达到最小证据数量；
- 对高敏感画像要求用户确认；
- 支持逐条确认、纠正和删除。

#### Skill

自动抽取默认进入 Draft。以下场景可以自动成为 Verified：

- 个人低风险模式；
- 不包含敏感信息；
- 与已有 Skill 不重复；
- 有明确触发条件、可执行内容和验证方式；
- 来源任务有明确成功信号。

团队共享、高风险和生产运维 Skill 默认要求审批。

## 6. 冲突与优先级

### 6.1 统一优先级

建议固定以下决策顺序：

```text
当前用户明确指令
  > 当前任务的显式约束
  > Verified Skill
  > 最近且高置信的 L1
  > Verified Persona
  > L2 场景总结
  > Draft 或旧背景信息
```

### 6.2 冲突处理原则

- 高优先级内容不能被低优先级内容静默覆盖；
- 新事实与旧事实冲突时保留冲突记录，不立即销毁证据；
- Skill 与用户当前指令冲突时，以当前指令为准，并记录 Skill 可能过期；
- Persona 与近期明确陈述冲突时，Persona 自动降权并进入待确认；
- 多个 Skill 冲突时，优先使用作用域更精确、版本更新、已验证且任务匹配度更高的 Skill；
- 高风险场景无法消解冲突时，不自动执行，要求用户确认。

## 7. 风险分级产品模式

统一数据模型之上提供三档策略，避免治理过重损害个人体验。

### 7.1 Personal 模式

适用个人助理和本地研发助手。

- L1 可自动晋升；
- 低风险 Skill 可自动发布；
- 用户可随时查看和撤销；
- 敏感信息扫描仍然强制启用；
- Persona 仍要求跨会话证据。

### 7.2 Team 模式

适用团队共享 Agent。

- 个人资产与团队资产分开；
- 团队 Skill 默认审批；
- 变更必须保留审计和版本；
- 冲突、重复和过期提示可见；
- 只有 Verified 团队资产可以作为强规则注入。

### 7.3 High-Risk 模式

适用生产运维、安全、财务、法律和合规场景。

- Skill 必须审批；
- 只允许 Verified Skill 影响执行；
- Draft Memory 只能作为带来源的参考；
- 敏感信息检测和保留策略不可关闭；
- 冲突时停止自动执行；
- 所有关键召回和 Skill 使用必须可审计。

## 8. 分阶段迭代路线

## Phase 1：可信基础

### 目标

让用户和 Agent 清楚知道：系统记住了什么、来源是什么、为什么会生效，以及如何纠正和删除。

### 核心能力

- 为 Memory 与 Skill 建立统一治理元数据；
- 补齐来源引用和派生关系；
- 增加 Draft/Verified 等生命周期状态；
- 提供 Memory 与 Skill 管理入口；
- 支持确认、纠正、拒绝、归档和删除；
- 建立 L0 到 L1/L2/L3/Skill 的派生关系；
- 实现删除影响预览和删除传播；
- 在召回上下文中区分事实、推断和规则；
- 提供“为什么召回这条内容”的基础解释。

### 产品结果

用户能够完成完整闭环：

```text
查看长期资产
→ 查看来源
→ 确认或纠正
→ 查看影响范围
→ 删除
→ 验证后续不再召回
```

### 成功指标

- 来源引用覆盖率；
- 可解释召回覆盖率；
- 删除传播成功率；
- 删除后残留率；
- 用户纠正闭环成功率；
- 无来源的 L2/L3/Skill 占比；
- Memory/Skill 管理功能使用率。

### 阶段出口条件

- 所有新生成长期资产都有来源和状态；
- 用户可以完成查看、纠正和删除；
- 删除后不会继续从已知派生资产召回；
- 交付层可以向 Agent 区分事实、推断和行为规则。

## Phase 2：质量治理

### 目标

降低低质量、重复、冲突、过期和敏感资产进入正式召回链路的概率。

### 核心能力

- Draft/Verified 正式生效；
- Personal、Team、High-Risk 策略分级；
- Skill 候选审批；
- Persona 严格晋升；
- 相似 Skill 与相似 L1 聚类；
- 冲突中心和处理流程；
- Secret、Token、PII 和敏感内容扫描；
- 自动过期、降权和 Deprecated 状态；
- 低质量 Skill 评分；
- 对 fail-open 去重期间写入的数据进行后台再治理。

### 成功指标

- Draft 采纳率；
- Draft 拒绝率；
- 正式资产误发布率；
- Skill 重复率；
- Memory 冲突率；
- 冲突平均解决时长；
- 敏感信息写入拦截率；
- Persona 被用户纠正的比例；
- 过期资产仍参与召回的比例。

### 阶段出口条件

- 团队和高风险模式不存在未经审批的正式 Skill；
- 敏感信息检测覆盖所有长期资产写入口；
- 冲突不会被静默覆盖；
- Persona 具备严格晋升和降级路径；
- 相似与过期资产可以被识别和治理。

## Phase 3：交付优化

### 目标

在可信资产基础上，提高有效召回率、Skill 命中质量和上下文效率。

### 核心能力

- Memory 与 Skill 统一编排；
- 根据任务风险、资产状态、置信度和作用域决定注入；
- 独立预算 L1、Persona、Scene Navigation 和 Skill；
- 低置信内容以“待验证参考”注入；
- 高风险任务只使用 Verified Skill；
- Skill 路由融合名称、BM25、Embedding、任务类型和历史使用效果；
- 为 Agent 提供结构化召回解释；
- 增加 Gateway 断连本地暂存与恢复补传；
- 增加记忆处理状态反馈，减少“刚记住但暂时搜不到”的困惑。

### 成功指标

- 有效召回率；
- 错误召回率；
- Skill 正确路由率；
- 召回内容被 Agent 实际采用的比例；
- 上下文平均占用；
- P95 召回延迟；
- Gateway 故障期间的数据补传成功率；
- 用户因错误记忆进行纠正的频率。

### 阶段出口条件

- 错误召回率达到产品目标；
- 不同风险等级使用不同交付策略；
- 上下文预算有明确上限；
- 断连不会造成不可恢复的记忆缺失；
- Agent 可以解释每类长期信息的来源和权威级别。

## Phase 4：受控自我改进

### 目标

根据真实使用效果持续改善资产质量，但不允许模型无监督修改高风险正式资产。

### 核心能力

- 记录资产被召回、查看、采用和忽略；
- 关联任务结果和用户纠正；
- 根据使用效果调整排序；
- 识别长期未使用或频繁被纠正的资产；
- 生成合并、降级、过期和修订建议；
- 对 Personal 模式允许低风险自动修订；
- Team 与 High-Risk 模式只生成建议，继续走审批；
- 建立治理策略 A/B 测试和离线评测集。

### 成功指标

- 长期资产有效贡献率；
- Skill 命中后的任务成功率；
- 被频繁忽略的资产占比；
- 自动治理建议采纳率；
- 资产被修订后的效果提升；
- 旧资产自然退出正式召回链路的比例；
- 自我改进导致的回归率。

### 阶段出口条件

- 资产排序能够利用真实结果反馈；
- 低价值资产可以被识别并退出；
- 自动改进有明确权限边界、审计和回滚；
- 高风险正式资产始终保留人类控制权。

## 9. 产品指标体系

### 9.1 北极星指标

建议采用：

> 长期资产有效贡献率：被 Agent 实际采用、对任务有帮助，并且未被用户纠正或撤销的 Memory/Skill 占所有被交付长期资产的比例。

该指标同时约束召回质量、资产质量和实际任务价值，比记忆数量、Skill 数量或单纯点击率更接近产品目标。

### 9.2 核心效果指标

- 有效召回率；
- 错误召回率；
- Skill 正确路由率；
- Skill 使用后任务成功率；
- 用户确认率；
- 用户纠正率；
- Persona 稳定性；
- Draft 到 Verified 转化率。

### 9.3 安全约束指标

- 敏感信息写入率；
- 未审批高风险 Skill 发布率；
- 删除残留率；
- 跨作用域错误召回率；
- 冲突静默覆盖率；
- 无来源正式资产占比。

这些指标应设为硬约束，不能为了提高召回率而放宽。

### 9.4 成本与性能指标

- 单轮召回字符和 Token 占用；
- L1/L2/L3 平均生成成本；
- 单个 Skill 抽取成本；
- P50/P95 召回延迟；
- 队列等待时间；
- transient 重试资源消耗；
- 每千次对话新增长期资产数量；
- 每个活跃用户的长期资产增长速度。

## 10. 关键产品界面

### 10.1 “系统记住了什么”页面

统一展示：

- L1 事实；
- 场景记忆；
- Persona 条目；
- Draft Skill；
- Verified Skill。

每条资产展示：

- 类型和状态；
- 作用域；
- 来源；
- 置信度；
- 创建原因；
- 最近验证时间；
- 最近使用时间；
- 冲突和派生关系。

### 10.2 Skill 候选审批页

提供：

- 对话来源；
- 新建或修改差异；
- 相似 Skill；
- 敏感信息告警；
- 建议作用域；
- 预期触发条件；
- 发布、修改、拒绝和合并操作。

### 10.3 冲突中心

展示：

- 新旧事实冲突；
- Persona 与近期陈述冲突；
- Skill 与当前团队规则冲突；
- 多个 Skill 互相矛盾；
- 删除原始证据后仍存在的派生资产。

### 10.4 召回解释

允许用户查看某次回答中：

- 哪些 Memory 被召回；
- 哪些 Skill 被路由；
- 为什么命中；
- 哪些内容实际进入 Prompt；
- 哪些内容因预算、风险或状态被过滤；
- Agent 是否实际采用。

## 11. 数据迁移原则

### 11.1 兼容优先

现有 L1/L2/L3 和 Skill 不应在升级时直接视为 Verified。建议：

- 有明确来源和近期使用记录的资产迁移为 Verified 或 Legacy-Verified；
- 无来源或来源不可恢复的资产迁移为 Draft/Legacy；
- 现有 Persona 拆分为可独立确认的条目；
- 现有 Skill 保留版本与 owner/team 关系；
- 迁移过程不物理删除旧数据。

### 11.2 双读阶段

在治理字段上线初期，允许旧数据与新数据双读，但交付层应明确标记 Legacy 资产并降低默认权威级别。

### 11.3 可回滚

所有迁移都应支持：

- dry-run；
- 数量和范围报告；
- 迁移批次 ID；
- 回滚；
- 数据一致性校验；
- 旧版客户端兼容窗口。

## 12. 主要风险与缓解策略

### 12.1 治理模型增加系统复杂度

风险：状态、来源、派生图和冲突关系会增加存储、接口和迁移复杂度。

缓解：先实现最小公共字段和最关键状态，不在 Phase 1 一次性建设完整知识图谱。

### 12.2 审批过重损害个人体验

风险：每条 Memory 和 Skill 都要求确认，会让产品难以使用。

缓解：使用 Personal、Team、High-Risk 三档策略；个人低风险资产允许自动晋升，审批集中在敏感、冲突和高影响资产。

### 12.3 晋升过严导致召回下降

风险：可信度提升但 Agent 失去跨会话连续性。

缓解：Draft 可以作为明确标记的低权威参考参与个人模式召回，但不能作为强规则或高风险执行依据。

### 12.4 来源和删除传播不完整

风险：历史资产缺少消息引用，无法精确计算删除影响。

缓解：对旧资产标记 Legacy 和来源不完整；新资产强制建立派生关系；删除旧数据时提供保守清理和人工确认。

### 12.5 指标被错误优化

风险：团队为了提高有效召回率减少召回量，或者为了提高采纳率只交付安全但无价值的信息。

缓解：北极星指标必须与错误召回率、任务成功率、覆盖率和用户纠正率联合评估。

## 13. 当前明确暂缓事项

在 Phase 1 和 Phase 2 完成之前，建议暂缓：

- 增加 L4/L5 等新记忆层级；
- 全面提高自动捕获和自动发布比例；
- 允许 Review Agent 自动删除正式 Skill；
- 允许模型自动改写团队与高风险正式 Skill；
- 大规模替换全部存储后端；
- 仅通过升级更大模型解决错误抽取；
- 建设复杂的全量知识图谱；
- 将所有历史数据一次性标为高置信 Verified；
- 以 Skill 创建数量或 Memory 数量作为团队绩效目标。

## 14. 建议的决策顺序

后续产品和架构评审应按以下顺序做决策：

1. 明确统一治理元数据和生命周期；
2. 明确作用域、风险等级和权限；
3. 明确来源、派生与删除传播语义；
4. 明确冲突优先级；
5. 明确产品管理和审批体验；
6. 明确召回交付协议；
7. 明确指标和评测集；
8. 最后再决定存储、队列和模型实现细节。

## 15. 最终方向

TencentDB Agent Memory 后续不应只定位为“帮助 Agent 记住更多内容的基础设施”，而应逐步定位为：

> 管理 Agent 长期事实、推断和行为规则的可信资产平台。

Chat Memory 负责保存证据和形成不同粒度的长期理解；Skill 负责保存未来可执行的行为方法；治理层负责决定哪些内容足以被信任；交付层负责在正确的任务、作用域和风险条件下把正确资产交给 Agent。

当系统能够解释每条长期资产的来源，允许用户纠正和删除，并根据真实任务结果持续淘汰低价值内容时，Memory 与 Skill 才真正从“自动记录功能”升级为可信的长期 Agent 能力。
